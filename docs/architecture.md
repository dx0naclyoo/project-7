# Архитектура проекта

## Структура

Код разделён по темам. В каждой теме четыре файла:

    src/users/
      schemas.py      данные запроса и ответа (Pydantic)
      router.py       ручки: только HTTP
      service.py      правила работы (например, "нет пользователя: 404")
      repository.py   SQL-запросы

Так же устроены `src/parameters/` и `src/goals/`. Общее подключение к БД лежит в `src/db.py`,
сборка приложения в `main.py`, структура таблиц в `migrations/postgresql/`.

## Слой сервисов: да

Ручка принимает запрос и возвращает ответ. Правила живут в сервисе, SQL в репозитории.
Причины:
- SQL лежит в одном месте, его легко найти и поменять;
- правила можно проверять тестами без HTTP и базы;
- код не дублируется при росте проекта (тренировки, калории, уведомления).

## Правило вызовов

router вызывает service, service вызывает repository, repository ходит в БД.
Слой знает только о слое ниже. Репозиторий ничего не знает о HTTP, поэтому он возвращает
данные или True/False, а ошибки (404, 500) формирует сервис.

Сервисы параметров и целей проверяют пользователя через `UserRepository.exists`.

## Почему не entities, tables, handlers

Группировка по темам удобнее при росте: всё про пользователей лежит в одной папке.
Папки tables нет: таблицы описаны миграциями, ORM в проекте нет. Если появится ORM,
модели таблиц будут лежать в папке темы рядом с остальными файлами.
